## Fallos observados y corregidos

1. El CLI 2.39.5 falla al importar el error workflow sin ID:
   `SQLITE_CONSTRAINT: NOT NULL constraint failed: workflow_entity.id`.
   `local-up.sh` ahora genera un UUID dentro de la instancia si no existe uno
   y lo aplica solo a archivos temporales; al reimportar conserva el ID existente.
2. Sin publicar el error workflow, el runtime rechaza su ejecución como
   `is not active and cannot be executed`. El arranque ahora publica también
   `error-agente`; la prueba real exige que el error alcance al AgentRun.
3. La prueba de arranque cubre ID nuevo/existente, publicación de los tres
   workflows, fallo de importación y eliminación de temporales sin secretos.

## Preparación de la instancia productiva

La API de #113 está en `main` `508705f` (release #149), con CD
[`38783393634`](https://github.com/bryancito1090/istpetdev-platform/actions/runs/38783393634)
exitoso. Se verificaron con el cliente M2M existente los endpoints de lookup y
failure usando IDs inexistentes: ambos devolvieron 404, sin crear ni alterar un
AgentRun. El inventario de n8n remoto encontró ambos workflows activos, sin
`settings.errorWorkflow` ni el nodo `Register Execution`.

Hay respaldo privado 0600 fuera del repositorio. El cambio preparado conserva
el grafo existente y sus credenciales, añade el registro de ejecución y el ID
en la respuesta 202, configura el workflow de error y publica los tres. Antes
de escribir se compara la versión remota para detectar ediciones concurrentes.
No se hacen resets, interrupciones ni inyecciones de fallo en la API productiva.
Después de la corrida aislada verde, el 15-oct a las 19:01 UTC, se aplicó ese
cambio acotado. La API pública de n8n asignó el ID de `error-agente`; el ID se
conserva solamente en la instancia. Se leyó de vuelta que el handler y ambos
workflows están publicados en su versión actual, vigía/incidente tienen el
vínculo correcto y `Register Execution`, y el Schedule continúa apagado. Se
reutilizó la misma credencial M2M de `Send Result`, sin crear credenciales.

Verificación posterior: firma inválida → 401 en ambos webhooks; API readiness
200. El runtime de excepción/fallback se probó en la instancia aislada real;
la configuración/publicación se comprobó también en producción. No se indujo
una excepción ni una caída en los workflows productivos, ni se hicieron resets
de datos productivos.
